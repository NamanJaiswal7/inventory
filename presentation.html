Phase 1: The Problem

Warehouse Ingestion at Scale

📦 Domain Components

1. Physical Box (Unique)

Has an individual barcode (BAR-821D) and physical shelf coordinates (AISLE-1-SHELF-3).

2. Catalog Product (Heavy)

Has SKU, product title, and a heavy 5 MB high-res photo/specification payload.

⚠️ The Dual Architectural Violations

1. Memory Bloat (No Flyweight): NaiveInventoryItem allocates a new 5MB byte array for every single box. Receiving 1,000 boxes allocates 5,000 MB (5 GB), instantly crashing standard JVM heaps with OutOfMemoryError.
2. Tight Coupling (No Factory Method): NaiveShipmentProcessor uses a rigid switch(type). Adding "Toys" or "Groceries" violates the Open/Closed Principle (OCP).
Solution: Structural Pattern

The Flyweight Pattern

"Use sharing to support large numbers of fine-grained objects efficiently."

1. The Flyweight
ProductCatalogItem

Stores Intrinsic State: Invariant and immutable. Holds the SKU, title, and the heavy 5MB image buffer.

✅ Allocated exactly once per unique SKU.
2. The Flyweight Factory
ProductCatalog

Thread-safe registry utilizing ConcurrentHashMap. Ensures no duplicate Flyweights ever exist in heap memory.

computeIfAbsent(sku, ...)
3. The Context
OptimizedInventoryItem

Stores Extrinsic State: Barcode and shelf location. Holds an 8-byte pointer to the shared Flyweight.

⚡ Footprint: ~40 bytes (vs 5MB!)
1,000 Items Memory Cost: Naive: 1,000 × 5MB = 5,000 MB vs Flyweight: (1 × 5MB) + (1,000 × 40B) ≈ 5.04 MB 99.8% Savings
Solution: Creational Pattern

The Factory Method Pattern

"Define an interface for creating an object, but let subclasses decide which class to instantiate."

The Creator (Abstract Base Class)
ShipmentReceiver

Encapsulates the standard warehouse receiving loop in processShipment(count), delegating individual item construction to:

protected abstract OptimizedInventoryItem createInventoryItem(String barcode, String location);
Concrete Creators
ElectronicsReceiver
BooksReceiver
ClothingReceiver

Each subclass binds its specific SKU to the shared Flyweight catalog and returns the context item.

Spring DI Dynamic Registry
ShipmentReceiverRegistry

By injecting List<ShipmentReceiver> into the constructor, Spring automatically discovers all concrete receivers on the classpath.

✅ No switch or if/else statements anywhere in the controllers.
✅ Open for Extension: Adding ToysReceiver requires creating a new class; zero existing classes are modified.
✅ Closed for Modification: Core intake engine is immutable.
100% Compliant with Open/Closed Principle (OCP)

Conclusion

Summary of Key Architectural Principles

1. Flyweight Pattern

  • • Intrinsic State: Kept in ProductCatalogItem (SKU, title, 5MB image).
  • • Extrinsic State: Kept in OptimizedInventoryItem (barcode, aisle shelf).
  • • Factory Registry: ProductCatalog uses thread-safe ConcurrentHashMap.computeIfAbsent.
  • • Verdict: Essential whenever massive object volume causes severe memory duplication.

2. Factory Method Pattern

  • • Abstract Creator: ShipmentReceiver standardizes batch loops.
  • • Concrete Creators: ElectronicsReceiver, BooksReceiver implement creation.
  • • OCP Compliant: New categories can be introduced via new classes without modifying existing code.
  • • Strategy Registry: Spring DI automatically discovers and maps all receivers.

"Architecture is about separating what changes from what stays the same, and sharing what is identical."
