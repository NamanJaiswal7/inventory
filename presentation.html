Step 1: The Engineering Foundation

Why Do We Need Design Patterns?

"Why not just write simple, direct code? Why add layers of design?"

Crisis #1: Physical Hardware Limits
The Memory & Resource Boundary

In toy programs with 5 items, any code works. But in real-world high-throughput platforms (Amazon, Netflix, Uber):

  • ❌ RAM is finite: Careless object allocation creates millions of duplicated objects, saturating the heap and triggering catastrophic OutOfMemoryError.
  • ❌ Garbage Collection Pause: Constant allocations cause frequent stop-the-world GC cycles, freezing server response times.
Crisis #2: The Software Evolution Reality
The Coupling & Change Fragility

Business requirements change constantly. New products and workflows are introduced weekly:

  • ❌ Rigid Spaghetti Code: Without patterns, developers use massive switch/if-else chains. Every new feature requires editing existing core code.
  • ❌ Violation of Open/Closed Principle: Modifying existing production files introduces regression bugs and expensive re-testing cycles.
💡 The Core Premise: Design patterns are not theoretical exercises—they are proven architectural patterns to prevent system crashes and code decay.
Step 2: The Domain Scenario

The Problem in our Warehouse Ingestion

The Real-World Domain Data
Physical Item (Box on Shelf): Unique to each box: Barcode (BAR-821D) and location (AISLE-1-SHELF-3).
Product Catalog Entry: Identical for all boxes of this product: SKU, Title, and heavy 5 MB high-resolution photo/spec buffer.
What Happened Without Design Patterns (Naive Code)
1. Memory Bloat (No Flyweight): Every single box allocated its own 5MB byte array.
1,000 items × 5 MB = 5,000 MB (5 GB RAM)!
Server exhausted heap and crashed with OutOfMemoryError.
2. Tight Coupling (No Factory Method): NaiveShipmentProcessor used hardcoded switch(type). Adding a product requires modifying existing processor code (violates OCP).
1,000 Boxes Shipment → 5 GB Heap Allocated → Server Crashed & Dead Code Architecture
Step 3A: The Memory Solution

How Flyweight Resolves the 5 GB Memory Crash

1. The Flyweight
ProductCatalogItem

Holds Intrinsic State: Invariant and immutable. Holds SKU, title, and the heavy 5MB image buffer.

Allocated ONCE per SKU
2. The Flyweight Factory
ProductCatalog

Thread-safe registry utilizing ConcurrentHashMap. Uses atomic computeIfAbsent() to cache singletons.

Thread-Safe Singleton Cache
3. The Context
OptimizedInventoryItem

Holds Extrinsic State: Unique barcode, shelf location, and an 8-byte reference pointer to the Flyweight.

Footprint: ~40 Bytes (vs 5MB!)
Memory Math for 1,000 Items: Naive: 5,000 MB (Crash) → Flyweight: 1 × 5 MB + (1,000 × 40B) ≈ 5.04 MB 99.8% Savings
Step 3B: The Coupling Solution

How Factory Method Resolves Tight Coupling (OCP)

The Creator (Abstract Base Class)
ShipmentReceiver

Standardizes the universal batch loop in processShipment(count), but delegates item instantiation to the abstract factory method:

protected abstract OptimizedInventoryItem createInventoryItem(String barcode, String location);
Concrete Creators (Subclasses)
ElectronicsReceiver
BooksReceiver
ClothingReceiver

Each subclass implements createInventoryItem() to resolve its Flyweight from the catalog.

Spring DI Registry (Zero Switch Statements)
ShipmentReceiverRegistry

Spring auto-injects all List<ShipmentReceiver> into a dynamic lookup map at startup.

✅ Closed for Modification: Core shipment engine is frozen and safe from regressions.
✅ Open for Extension: Adding GroceriesReceiver requires only creating a new class with @Component. Zero existing files are touched!
Open/Closed Principle (OCP) Fully Satisfied

Conclusion

Summary of Key Architectural Principles

1. Flyweight Pattern (Structural)

  • • Separates invariant Intrinsic State from context-dependent Extrinsic State.
  • • Caches heavy payloads in a thread-safe factory registry.
  • • Shrinks heap footprint by 99.8% in high-volume batch processing.

2. Factory Method Pattern (Creational)

  • • Standardizes workflow in an abstract creator, deferring instantiation to subclasses.
  • • Completely eliminates rigid conditional switch blocks.
  • • Satisfies the Open/Closed Principle (OCP) via Spring component discovery.

"Architecture is about separating what changes from what stays the same, and sharing what is identical."
